# JOJO-Recompiled: path to first playable backend

## Goal
Reach the first genuinely playable Windows build without falsely marking the installation `native-ready` before the game-specific backend can boot and run the user-provided game data.

## Execution order
1. [x] Expand SH-4 integer/control coverage with test-first increments.
2. [x] Add unsupported-opcode census/reporting so future instruction work is prioritized by actual executable coverage rather than guesswork.
3. [x] Model the remaining architectural SH-4 state needed by real code: status/control registers, exception return, banked registers, dynamic shifts/rotates, MAC operations and FPU.
4. [x] Build a Dreamcast executable loader and deterministic memory map for the analyzed boot executable. **M3.1 complete (100%).**
5. [ ] Add MMIO/device boundaries and deterministic timing surfaces required to get from reset/bootstrap into game code.
6. [ ] Implement the minimum PVR2/video, Maple/input, GD-ROM/data access and AICA/audio behavior needed for first interactive gameplay, keeping rendering/audio adapters outside deterministic gameplay state.
7. [x] Introduce a production native-runtime path that emits and executes x86-64 machine code for covered blocks while retaining the reference executor as an explicit fallback/oracle for blocks that do not yet have a dedicated machine-code lowering. **M3.2 complete; M3 complete (100%).**
8. [ ] Mark conversion output `native-ready` only after an end-to-end test proves that the generated installation launches through `JOJO-Recompiled.exe` into an interactive game state using user-provided legally obtained data.
9. [ ] After first playable, harden performance, graphics/aspect handling, controls, mods, training instrumentation and rollback networking against the approved design.

## M3.2 completion evidence

- RED head `11554ef14f2d5b116f2a45ea2f96b298ae9bc70c`: CI #544 failed exactly because `core/native_backend.h` and the production native-runtime/cache API did not exist yet.
- The first GREEN architecture pass established deterministic runtime state, cache reuse/rebuild and explicit fallback behavior; CI #548 and the independent invalidation regression CI #549 passed Linux and Windows/MSVC.
- Final native-code RED `83c16122d6cbe3a6a3b03d936fdfbf8f928e3839`: CI #553 failed exactly because the backend still lacked persisted executable `native_code`, a `native_code_executed` proof and native-code byte accounting.
- Final GREEN `075b1aa183a8722d35fc97f78755feecff015bff`: CI #563 passed Linux x86-64 and Windows x64/MSVC. The synthetic regression therefore executes generated machine code under both SysV x64 and Windows x64 calling conventions and reaches the expected SH-4 state without reference fallback.
- Eligible straight-line SH-4 IR blocks emit real x86-64 instructions. The initial machine-code lowering covers `NOP`, T-bit clear/set/move, `MOV #imm`, `ADD #imm`, register move and register add; uncovered/control-flow blocks remain explicit reference fallbacks rather than being mislabeled native.
- Generated bytes execute from RX memory (`mmap`/`mprotect` on Linux and `VirtualAlloc`/`VirtualProtect` on Windows). The backend ABI is host-ABI-specific so incompatible Windows/SysV code caches cannot be reused across calling conventions.
- `create_native_runtime()` owns prepared executable memory, CPU state and compiled backend. `step_native_frame()` advances generated code deterministically, tracks a frame index and hashes CPU + the complete 16 MiB RAM backing for deterministic state comparison.
- `<converted-game>/cache/native/backend_cache.ini` records ABI/core/program identity and native-code byte count. `<converted-game>/cache/native/compiled_plan.bin` persists both reloadable IR/control-flow data and the generated machine-code bytes themselves.
- Cache reuse is verified when identity matches; rebuild is independently verified for stale `core_version`, stale backend ABI and changed program content.
- No game image, extracted game bytes, commercial fingerprint or generated copyrighted asset is present in the implementation or tests.

**M3 — Native recompiler backend: Complete (100%) by the architecture criteria in `docs/architecture/PRODUCTION-ROADMAP.md`.** This is deliberately narrower than “game playable”: not every IR operation has a dedicated x86-64 lowering yet, reference fallback remains explicit for non-lowered blocks, and the conversion manifest remains non-`native-ready`. Steps 5, 6 and 8 still require real device behavior, real game boot/frame/input evidence and legally supplied game data.
